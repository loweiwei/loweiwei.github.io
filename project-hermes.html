跨校（成大）生成式 AI 與應用期末專題

這個專題的核心問題是：LLM 可以產生 SQL、Python code 或 bug report，但「看起來合理」不等於「格式正確、可以執行、真的符合任務」。因此我把 LLM 放在語意理解與候選答案生成的位置，再用 deterministic wrapper 負責格式檢查、靜態分析、程式執行、mutation testing、fallback 與結果檔輸出。

Project Story

專題定位：不是讓 Agent 自己說自己對，而是讓程式驗證能檢查的部分

在 Text2SQL、程式生成、除錯報告與測試選擇這類任務中，LLM 的優勢是理解自然語言、推測使用者意圖與產生候選答案；但它的弱點也很明顯：可能輸出錯誤 JSON、引用不存在的欄位、產生不能執行的 Python、把 clean code 誤判為 buggy，或用自然語言宣稱某個測試能殺死 mutant，卻沒有真的執行過。

Hermes 的設計因此採用一個簡單原則：LLM for reasoning, deterministic system for trust。模型負責提出 candidate answer，wrapper 負責把 candidate 轉成可檢查的 contract，並用 schema validation、AST checks、sample execution、dynamic probes、reference/mutant execution 等方式產生客觀證據。

我想解決的問題

降低 LLM 在軟體工程任務中「輸出看起來合理，但 evaluator 無法讀取或實際執行錯誤」的風險。

我的主要貢獻

實作四個可執行 Skill wrapper，包含 SQL 驗證、Python AST 與 sample checks、Bug report normalization / dynamic audit，以及 mutation-test kill matrix selection。

讀者可以怎麼理解

把 Hermes 想成一個可重跑的交付流程：模型先產生候選答案，程式再檢查能不能安全交給評分器。

System Architecture

整體架構：任務進來後，正式答案必須經過 wrapper 才能輸出

每個 Skill 都遵守同一個高階流程：課程 evaluator 或本地 run_dev.py 組成 payload，Hermes / LLM 根據任務產生候選答案，接著呼叫該 Skill 的 scripts/run.py。runner 解析 payload 與 candidate，進行靜態或動態檢查，最後把正式 JSON 寫到 AIASE_RESULT_PATH。正式答案不是聊天文字，也不是 stdout 裡的一段說明，而是一份可被 evaluator 穩定讀取的 JSON result file。

Four Agent Skills

四個 Skills 的共同精神：能用程式檢查的，就不要只相信模型描述

這四個任務看似不同，但都遵守相同模式：LLM 產生 candidate，runner 檢查 candidate 是否符合 contract 與基本行為。如果 candidate 不可靠，runner 會把錯誤轉成可控的 fallback，而不是讓 evaluator 收到不合法輸出。

01

Text2SQL

自然語言問題 → SQLite SELECT query

風險是 LLM 可能產生 fenced SQL、多 statement、DDL/DML、ambiguous column，或引用不存在的 schema 欄位。

Question + SchemaLLM SQLClean FenceRead-only CheckSQLite EXPLAINSafe SQL JSON

LLM：理解 table、join、filter、aggregation 語意。

Wrapper：移除 Markdown fence、遮蔽字串與註解後檢查危險 keyword，使用 schema-aware validation 和 SQLite EXPLAIN，失敗時輸出 SELECT NULL WHERE 0。

02

Code Author

題目描述 → 可交付 Python function

風險是候選 code 可能沒有 entry function、違反 import policy、hardcode samples、無限迴圈，或在主 process 執行時造成 evaluator 不穩。

Task + SamplesLLM CodeAST ParseSLOC / Import PolicyWorker SamplesBest Candidate

LLM：根據題目與 constraints 產生 candidate function。

Wrapper：檢查 AST、entry point、dangerous calls、sample hardcoding，並在 child process 中執行 samples；候選失敗時使用 deterministic template 或低信心 stub。

03

Bug Hunter

Python code → 可定位 bug report

風險是 LLM 可能輸出不合法 JSON、行號錯誤、enum 不符合規格、過度猜測，或在 clean code 上亂報 bug。

Task + CodeLLM ReportJSON ExtractNormalize LinesDynamic AuditFinal Contract

LLM：提出可能 bug、位置、嚴重度與修正方向。

Wrapper：抽出 JSON、修正 line range、映射 invalid enum、過濾 placeholder/speculative report，並用 task-family probes 補強可執行證據。

04

Open Test Killer

Reference + Mutants + Inputs → 最有效測試集合

這是本專題最接近 deterministic evaluator 的部分。測試能否 kill mutant 不是用模型猜，而是實際執行 reference 和 mutants 後建立 kill matrix。

Reference + MutantsCandidate InputsExecute ProgramsBuild Kill MatrixExact / Greedy SelectKill Rate

LLM / Hermes：主要負責把完整 payload 傳給 runner。

Wrapper：執行 reference 與 mutants，定義 exception / timeout / wrong output 為 kill，再用 exact maximum coverage 或 deterministic greedy fallback 選測試。

Verification Pipeline

驗證不是單一測試，而是多層防線

Hermes 的可靠性來自多個小而明確的工程決策：結果檔 contract、候選答案清理、靜態檢查、受限 worker 執行、fallback、self-tests、regression tests 與 repository verifier。這些機制不保證模型永遠答對，但能讓失敗變得可觀測、可重跑、可歸因。

Contract

AIASE_RESULT_PATH

每個 Skill 都把正式結果寫入指定 JSON 檔，避免把自然語言聊天回覆誤當成答案。

Atomic Write

Temporary File + Replace

先寫暫存檔，再用 os.replace() 交換，降低 evaluator 讀到半份 JSON 的機率。

Static Checks

SQL / AST / Policy

Text2SQL 檢查 read-only schema；Code Author 檢查 AST、entry function、SLOC、imports 與 dangerous calls。

Dynamic Checks

Worker Execution

候選 code、bug probes、reference/mutant execution 都透過 child process、timeout 與 resource limits 控制。

Fallback

Safe Failure

當 candidate 不合法時輸出可執行但低信心的結果，而不是讓 evaluator crash 或收到危險內容。

Regression

Self-tests + Verifier

用 root pytest、skill self-tests、regression scripts 和 repository verifier 檢查 contract 與邊界行為。

Open Test Killer Example

Kill Matrix 如何選出最有效測試

Open Test Killer 會先用每個 candidate input 執行 reference，得到 expected output；再用同一個 input 執行每個 mutant。若 mutant 的輸出不同、丟 exception 或 timeout，就代表這個 input 能 kill 該 mutant。最後在 max_tests 預算內選出覆蓋最多 mutants 的測試組合。

在下方範例中，Budget = 2 時選 A + B 可 kill M1、M2、M3，因此 kill rate = 100%。這個結果來自實際執行，而不是模型自然語言推測。

BM2A + C → 67%

Limits & Claims

誠實限制：這是可靠性工程，不是保證 LLM 永遠正確

這個專題展示的是「如何把 probabilistic LLM output 放進 deterministic engineering pipeline」。它可以降低 contract failure、execution failure 與部分可檢查錯誤，但不等於所有任務都有 100% accuracy，也不等於能安全執行任意惡意程式。

可以支持的 claim

專題實作了四個可執行 Skill，並在 LLM candidate 外加入 SQL validation、AST checks、dynamic probes、mutation execution 與 deterministic fallback。

不能過度宣稱

不能宣稱泛化到 Spider、HumanEval、SWE-bench 或所有 production code；public dev tasks 曾用於開發，不是完全 held-out benchmark。

安全限制

child-process limits 可降低 infinite loop、memory blow-up 與 process leak 風險，但不是完整 VM / kernel-level sandbox。

下一步

最有價值的延伸是用獨立 private suite 重新評測，並保存模型版本、逐題輸出、token cost、runtime 與 precision / recall breakdown。

Core Design Principle

LLM for Reasoning, Deterministic System for Trust

讓 LLM 做語意理解與候選生成，把格式、限制、執行結果與可重跑證據交給 deterministic verification。

生成不等於正確能驗證的就不要只靠模型判斷最終輸出必須具有明確 contract
